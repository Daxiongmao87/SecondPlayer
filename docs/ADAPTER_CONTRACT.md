# SecondPlayer Adapter Contract

This document is normative for emulator integrations.

## 1. Principle

An emulator adapter is a replaceable boundary around a stock emulator. Emulator-specific behavior must not leak into the SecondPlayer core.

A user should be able to delete one adapter implementation without changing the policy engine, scheduler, player model, generic controller state, or unrelated adapters.

## 2. Core-facing interface

Core code talks to an emulator only through `EmulatorAdapter`:

```python
class EmulatorAdapter:
    @property
    def game_name(self) -> str: ...

    def start(self) -> None: ...
    def is_running(self) -> bool: ...
    def capture(self) -> np.ndarray: ...
    def apply(self, player: int, state: ControllerState) -> None: ...
    def close(self) -> None: ...
```

The current interface is deliberately small. It can evolve when a concrete cross-emulator need is demonstrated, but must not grow merely to expose one emulator's implementation details.

## 3. Adapter-owned responsibilities

Each adapter owns all of the following when they are needed:

- locating or launching its emulator;
- isolated emulator configuration/session profiles;
- command-line construction;
- attaching to an already running emulator if supported;
- framebuffer acquisition;
- input injection;
- mapping logical SecondPlayer seats to emulator controller ports/subports;
- validating seat/topology support;
- bundled scripts/plugins that use stock emulator extension APIs;
- adapter-specific IPC;
- emulator/version compatibility checks;
- adapter-specific dependencies;
- adapter-specific `doctor` checks;
- cleanup of temporary adapter/session resources.

## 4. Core-owned responsibilities

Core owns:

- local model lifecycle;
- Laya policy execution;
- decision scheduling;
- logical player modes (`human`, `ai`, `disabled`);
- generic decision logging/statistics;
- adapter selection;
- passing opaque adapter options to the selected adapter;
- generic controller-state semantics for the currently supported console family.

Core must not parse emulator config files or depend on emulator binary names, window classes, joystick enumeration, scripting APIs, controller limits, or platform-specific capture/input mechanisms.

## 5. Configuration isolation

Core TOML uses:

```toml
[adapter]
name = "mesence"

[adapter.options]
...
```

`secondplayer.config` preserves `[adapter.options]` as an opaque dictionary. The selected adapter is solely responsible for defaults, schema validation and interpretation.

This prevents adding fields such as `snes9x_binary`, `mesen_lua_port`, `retroarch_core`, etc. to the global application configuration.

## 6. Dependency isolation

An adapter should not force unrelated users to install its dependencies when avoidable.

The removed Snes9x prototype violated this spirit by putting X11 capture and Linux uinput packages in the base dependency set. That implementation was useful for exploration but is not the v1 architecture.

For MesenCE, the preferred bridge uses stock Lua APIs and local IPC. Any Python package required only by that adapter should be adapter-scoped/optional rather than a core dependency.

## 7. Stock-emulator rule

The v1 target must work with a stock emulator build.

Allowed:

- bundled SecondPlayer scripts loaded through documented emulator scripting facilities;
- isolated runtime configuration generated by SecondPlayer;
- local sockets/pipes between the script and `secondplayerd`;
- ordinary emulator command-line flags.

Not allowed for v1:

- patching emulator source;
- maintaining a SecondPlayer fork of the emulator;
- binary injection/hooking solely to obtain framebuffer/input control;
- asking users to rebuild the emulator;
- requiring persistent edits to the user's normal emulator profile.

## 8. Observation rule

The AI should receive information available to a human player through the game image, not hidden RAM/game state.

An emulator API that exposes the rendered framebuffer is preferred over desktop/window capture because it is cleaner and avoids UI chrome, scaling and compositor dependencies. It remains a visual observation, not a hidden-state shortcut.

## 9. Input rule

Input should enter through the cleanest stock interface exposed by the emulator.

Priority order:

1. emulator-supported scripting/input API;
2. emulator-supported remote/controller API;
3. OS virtual controller/input only when no cleaner stock interface exists.

This ordering is why MesenCE is now preferred over the earlier Snes9x prototype.

## 10. Deletion test

Before merging an adapter, apply this test:

> If this adapter directory were deleted, would core SecondPlayer still import, configure, and test successfully?

If the answer is no because core references that emulator, the adapter is not sufficiently isolated.

## 11. v1 MesenCE reference implementation

The first conforming adapter lives entirely under `secondplayer/adapters/mesence/`.

Its current choices are adapter details, not core contracts:

- loopback TCP transport;
- stock command-line `.lua` loading;
- temporary `$HOME` with an isolated MesenCE `settings.json`;
- optional copying of the user's existing settings into that temporary profile;
- `emu.takeScreenshot()` PNG transport;
- `emu.setInput()` from `inputPolled`;
- `--testrunner` + `xvfb-run` for headless Linux testing;
- runtime adaptation around the MesenCE 2.2.1 `setInput` port-selection defect;
- full-system savestates via `emu.createSavestate()` / `emu.loadSavestate()` inside a one-shot `exec` memory callback, transported length-prefixed (`STATE`) and uploaded raw after a length header (`LOADSTATE`), so blobs are binary-safe.

None of these choices should be generalized into core configuration or engine APIs unless a future adapter demonstrates a genuine shared requirement.
